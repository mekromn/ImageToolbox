# ImageToolbox Reference Lab — Advanced Requirements

Date: 2026-08-23

Status: Approved scope. These requirements extend `REFERENCE_LAB_FEATURE_SPEC.md` and `GAIN_MAP_LAB.md`.

## Purpose

This document captures the advanced requirements approved after the initial Reference Lab and Gain Map Lab specifications. These are not optional brainstorming items; they are part of the intended product unless later explicitly deferred in project state.

# A. Advanced HDR / Ultra HDR / Gain Map requirements

## 1. Dual-rendition SDR/HDR editing

Ultra HDR editing must treat the SDR fallback and HDR rendition as related but independently controllable targets.

Required modes:

- edit SDR base while preserving/re-fitting the HDR target;
- edit HDR target while preserving/re-deriving the SDR base;
- linked edit that intentionally affects both renditions;
- explicit view of the SDR fallback at all times;
- dependency tracking so edits cannot silently invalidate the SDR/HDR relationship.

## 2. HDR Master controls

Add a high-level HDR Master stage with documented semantics:

- reference white;
- target peak / target headroom;
- highlight knee;
- shoulder / rolloff;
- black floor;
- maximum local boost;
- highlight protection;
- specular emphasis;
- HDR clipping limit;
- gamut/color-volume protection.

The HDR target generated by these controls is what Gain Map Lab attempts to reproduce across display headroom.

## 3. SDR/HDR reconstruction optimizer

Automatic Ultra HDR generation should be able to optimize the SDR rendition, gain-map image and gain-map metadata together instead of deriving a single naive map.

Optimization goals can include:

- low reconstruction error;
- high-quality standalone SDR fallback;
- smooth display-headroom transition;
- minimal halos/ringing;
- bounded local gain;
- chroma/hue stability;
- compact map resolution/precision where it does not reduce target fidelity.

The optimizer must be deterministic for a fixed algorithm version and parameter set.

## 4. SDR/HDR pair registration and alignment

Before deriving a gain map from separate SDR/HDR references, support:

- orientation normalization;
- subpixel translation;
- scale alignment;
- small rotation correction;
- optional local/optical-flow alignment;
- motion/ghost detection;
- confidence map;
- exclude/repair unreliable regions rather than generating false gain from misregistration.

## 5. Exposure-bracket HDR creation

Reference Lab should be able to create an HDR master from bracketed stills:

`bracketed exposures -> registration -> deghost -> linear HDR merge -> HDR master -> SDR rendition -> gain-map generation -> Ultra HDR export`

Support 2/3/5+ exposures where practical.

## 6. Gain-map resolution and encoding controls

Expert Gain Map Lab must expose/diagnose:

- gain-map width/height or downsample ratio;
- one-channel vs RGB gain map;
- interpolation/reconstruction method;
- map precision / quantization;
- map compression quality where format exposes it;
- dithering before quantization where beneficial;
- estimated file-size impact;
- reconstruction error impact.

## 7. Perceptual gain-map editing mode

In addition to raw map editing, provide intent-oriented controls such as:

- +N stops HDR highlight;
- reduce/increase specular glow;
- protect this shadow;
- increase local HDR peak;
- suppress local gain;
- preserve skin luminance/chroma.

The engine translates this intent into valid map + metadata changes.

## 8. Gain-map frequency separation

Provide separate broad/low-frequency gain shaping and high-frequency edge/specular protection to reduce haloing while preserving legitimate local HDR structure.

## 9. Automatic halo/ringing detector

Analyze gain-map gradients against SDR/HDR source edges and flag likely:

- bright halos;
- dark halos;
- ringing;
- edge overshoot;
- map misregistration.

Offer constrained edge-aware repair instead of indiscriminate blur.

## 10. HDR reconstruction-error analysis

For pair-derived or validated output, calculate and visualize:

- max error;
- mean/RMS error;
- percentile error;
- per-channel error;
- highlight-only error;
- shadow-only error;
- perceptual color difference where meaningful;
- spatial error heatmap.

## 11. Encode -> reopen -> validate

Reference-grade export must support a validation pass:

1. encode output;
2. reopen the encoded file through a clean decode path;
3. re-read profiles/gain-map metadata;
4. reconstruct HDR;
5. compare SDR and HDR renditions against intended outputs;
6. report discrepancies and block/flag Reference-grade success when tolerances are exceeded.

Do not assume an encoder preserved the requested state merely because encode returned success.

## 12. Ultra HDR integrity checker

Standalone analyzer for existing files:

- detect gain map;
- verify SDR fallback;
- report gain-map dimensions/channels/precision;
- report all metadata;
- validate ranges and direction;
- verify profile/CICP consistency;
- reconstruct HDR at multiple headroom ratios;
- detect suspicious or invalid metadata;
- calculate reconstruction/transition diagnostics where reference information is available;
- produce a human-readable integrity report.

## 13. Consolidated HDR metadata inspector

One panel should expose:

- ICC profile;
- CICP/NCLX or equivalent primaries/transfer/matrix information;
- bit depth;
- range;
- gain-map metadata;
- gain-map dimensions/channels;
- HDR/SDR ratio metadata;
- EXIF/XMP HDR-related fields;
- container/codec;
- Android-decoder interpretation;
- warnings when metadata sources disagree.

## 14. Headroom Lab

Presets plus continuous scrub:

- 1.0x SDR;
- 1.5x;
- 2x;
- 4x;
- 8x;
- metadata full-HDR ratio;
- actual current display ratio;
- arbitrary custom ratio.

## 15. Display-adaptation curve visualization

Visualize how gain-map contribution changes as display HDR/SDR ratio increases. Allow inspection of both metadata transfer behavior and representative pixel trajectories.

## 16. HDR color-volume / gamut analysis

Add luminance-aware gamut/color-volume diagnostics rather than only 2D chromaticity warnings:

- P3 / Rec.2020 target boundaries;
- out-of-gamut at current luminance;
- color-volume clipping warning;
- perceptual HDR gamut compression preview;
- distinguish luminance clipping from chroma/gamut clipping.

## 17. HDR scopes in absolute and relative modes

Where the source interpretation makes it meaningful, allow waveform/scopes to switch among:

- normalized encoded values;
- linear-light values;
- relative HDR headroom;
- nit-oriented/absolute luminance view;
- SDR-reference-relative view.

The scope must clearly label the representation being measured.

# B. Reference matching, recipes and reproducibility

## 18. Reference-image matching

Allow a target/reference image to guide manual or automated matching of:

- white balance;
- tone curve;
- exposure/contrast;
- color/chroma;
- selective color;
- optional gain-map response.

Provide alignment when images are intended to depict the same scene and numeric difference feedback.

## 19. Named edit snapshots / versions

Beyond undo/redo, allow named snapshots such as:

- Original;
- Natural;
- HDR Strong;
- Skin Protected;
- Export Candidate A/B.

Switch instantly between snapshots without destroying history.

## 20. Recipe / sidecar import-export

Export and import the complete non-destructive recipe including:

- operation graph;
- algorithm versions;
- masks;
- geometry transforms;
- gain-map source/generation state;
- gain-map metadata overrides;
- presets;
- output settings where requested;
- source identity/fingerprint.

Use an openly documented versioned schema. XMP interoperability can be added where semantics genuinely map; do not force unsupported operations into misleading XMP fields.

## 21. Per-operation algorithm versioning

Every operation must store an implementation/version identifier. Improving an algorithm later must not silently change the appearance of old recipes.

Migration rules:

- old recipe renders with its original algorithm version when available;
- optional explicit upgrade command;
- upgrade preview/diff before committing;
- deterministic migration notes in recipe/history.

## 22. Deterministic rendering mode

Scientific/regression workflows require repeatable output for the same source + recipe + renderer version.

Control or eliminate nondeterminism from:

- thread ordering;
- stochastic noise/dither seeds;
- preview timing;
- cache state;
- GPU approximations where exact CPU/reference validation is required.

Store any stochastic seed that materially affects rendered pixels.

# C. Quality, hardware and large-image architecture

## 23. Quality/performance telemetry and explicit fallback reporting

Expose when the runtime falls back from requested quality, for example:

- FP32 -> FP16;
- FP16 -> 8/10-bit;
- wide-gamut -> sRGB;
- HDR -> SDR;
- full-resolution -> reduced-resolution preview;
- requested reconstruction filter -> cheaper filter;
- GPU -> CPU or vice versa.

A fidelity-affecting fallback must never be silent in Reference/Maximum Quality modes.

## 24. Memory-aware full-resolution tiled processing

Support huge images without changing final pixels:

- tiled full-resolution processing;
- overlap/gutters based on operation radius;
- deterministic edge handling;
- global-statistics prepasses where an operation requires them;
- multipass spatial filters with equivalent tiled/monolithic behavior;
- bounded memory planner;
- export checkpoint/error recovery where practical.

## 25. Hardware capability report

Reference Lab diagnostics should report:

- Android/API level;
- CPU/GPU identity where available;
- display resolution/DPR;
- wide-gamut support/current mode;
- HDR types;
- current HDR/SDR ratio/headroom;
- bitmap/image precision supported by relevant APIs;
- available decoders/encoders and advertised bit-depth/HDR support;
- memory budget;
- which Reference Lab paths are hardware accelerated.

## 26. Device reference-fidelity verification screen

Run internal validation patterns/tests and show capability status as VERIFIED / FAILED / UNKNOWN rather than inferred claims, e.g.:

- sRGB reference path;
- P3/wide gamut;
- high-precision intermediates;
- physical 1:1;
- Ultra HDR presentation;
- gain-map encode/decode;
- HDR surface;
- deterministic export.

## 27. HDR/SDR batch laboratory

Batch operations should include:

- SDR -> Ultra HDR;
- HDR -> Ultra HDR;
- Ultra HDR -> controlled SDR;
- extract gain maps;
- regenerate gain maps;
- re-fit gain-map metadata;
- validate/integrity-check Ultra HDR;
- apply gain-map preset;
- batch export with per-file validation report.

## 28. Gain-map presets

Preset examples:

- Natural;
- Gentle;
- Specular;
- Bright Outdoor;
- Low-Light Protected;
- Portrait Safe;
- Display Conservative;
- Maximum Headroom.

Presets must alter documented generator/metadata parameters, not hide an unexplained multiplier.

## 29. Optional machine-assisted Smart Gain Map

Later, an explicitly semantic/assisted generator may detect concepts such as:

- sky;
- emissive lights;
- reflections/speculars;
- faces/skin;
- diffuse white objects;
- shadows/noise.

Requirements:

- always optional;
- clearly identified as semantic/creative assistance;
- generated masks/decisions inspectable and editable;
- non-ML deterministic generator remains available.

## 30. Dedicated Reference Lab workspace

Provide a coherent top-level workflow rather than scattering advanced tools across unrelated menus:

`VIEW | EDIT | GAIN MAP | MASKS | ANALYZE | COMPARE | EXPORT`

Existing ImageToolbox screens remain useful, but Reference Lab should feel like one integrated image laboratory.

# D. Additional architecture requirements discovered during completeness pass

These requirements are important to lock before implementation gets deep.

## 31. Explicit scene-referred vs display-referred pipeline stages

Every operation must declare whether it expects/produces scene-referred linear data, display-referred data, perceptual coordinates, or encoded output. Do not allow operations to accidentally run in the wrong transfer domain.

## 32. Color-profile provenance and conflict resolver

Support and audit ICC v2/v4 and relevant container signaling such as CICP/NCLX. When multiple metadata sources disagree:

- report every source;
- define deterministic precedence rules;
- allow expert override;
- preserve original metadata provenance in the recipe/audit record;
- never silently reinterpret color.

## 33. Alpha/premultiplication correctness

Transparent images need explicit handling of:

- straight vs premultiplied alpha;
- color transforms before/after premultiplication;
- filtering/resampling at transparent edges;
- HDR/wide-gamut values under transparency;
- export conversion.

Prevent dark/bright fringes caused by processing premultiplied values incorrectly.

## 34. Geometry and mask coordinate contract

Define one stable source-coordinate model for:

- crop;
- rotate/flip;
- perspective/lens corrections;
- brush masks;
- gradients;
- semantic masks;
- gain-map masks.

Reordering geometry operations must either correctly transform downstream masks or be prevented with an explicit dependency explanation. Masks must not drift after crop/rotation/resize.

## 35. Pixel provenance / render audit record

Reference-grade exports should optionally produce a machine-readable audit record containing:

- source fingerprint;
- source profile/transfer/bit depth;
- decoder path/version;
- recipe + operation versions;
- working representation;
- renderer/backend;
- export encoder/version;
- output profile/bit depth;
- HDR/gain-map metadata;
- validation results;
- hashes of relevant artifacts.

This is especially valuable for regression/debug/reference work.

## 36. Technical and creative LUT support

Support high-precision 1D/3D LUT import (e.g. `.cube`) with explicit classification:

- technical/color-management LUT;
- creative LUT.

Requirements:

- defined input/output color spaces;
- tetrahedral or other documented high-quality interpolation where appropriate;
- intensity/opacity for creative LUTs;
- LUT preview and clipping/gamut diagnostics;
- never silently apply a creative LUT in Reference mode.

## 37. Color-chart calibration / camera matching

Later Reference Lab should support chart-assisted calibration:

- detect/manual-mark color patches;
- compare measured patches with reference values;
- derive correction matrix/curve or LUT;
- report residual Delta-E;
- save reusable camera/lighting calibration preset;
- apply in an explicit technical calibration stage.

## 38. Technical geometry/lens correction stage

Add high-quality non-destructive:

- straighten;
- perspective/keystone;
- barrel/pincushion distortion;
- chromatic aberration correction;
- vignette correction;
- lens-profile support where reliable data exists.

These operations need recipe ordering and mask-coordinate semantics from the start.

## 39. Depth-map aware editing

Where an image contains a usable depth/portrait map, preserve and expose it as an optional mask source. Geometry changes must transform depth consistently. Never discard embedded depth metadata silently when an output format can preserve it.

## 40. Cross-backend conformance tests

If both CPU and GPU renderers exist, provide tests that compare them within documented tolerances. The fast preview backend and full-resolution export backend must not produce materially different edits without an explicit reason.

# Architecture decisions that must be fixed before deep implementation

The following are early-lock items because retrofitting them later would be expensive:

1. dual SDR/HDR rendition state model;
2. per-operation algorithm versioning;
3. stable geometry/mask coordinate system;
4. scene-referred/display-referred stage contract;
5. color-profile provenance/conflict resolution;
6. deterministic recipe rendering rules;
7. tiled full-resolution processing semantics;
8. encode-reopen-validation contract;
9. gain-map dependency/invalidation rules;
10. preview/export backend conformance requirements.

# Definition of done for advanced requirements

No advanced item is complete until implementation, documentation, tests, fallback behavior, color/HDR semantics, and continuity state are all updated together. Fidelity-affecting behavior must be objectively validated before being described as Reference-grade.
